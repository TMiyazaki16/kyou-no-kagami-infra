# file-issue — 条件から Issue を起票する

このスキルは汎用に書いてある。リポジトリ固有の値は、リポジトリ直下の `AGENTS.md` の「開発フロー」節にある **「スキルが参照する値」表** から読む。以下の `<リポジトリ>`・`<gh>`・`<検証スキル>` はその表の値に置きかえる。表が見つからないときは起票せず、Deroshi に確認する。

## 前提

- 起票するのは **Deroshi が条件（何を・なぜ・どこまで）を示したときだけ**。自分の判断で Issue を増やさない。作業中に気づいた別件は、報告に「起票候補」として書いて Deroshi に預ける
- `<gh> auth status` が成功していること。トークンの値を表示・記録・ファイルへ書き出ししない
- 起票は GitHub への書き込み。依頼の範囲を超えて Issue を作らない（試しに作って消す、もしない）

## 手順

1. **条件を読んでテンプレの 4 項目を埋める**（下の「テンプレ」）。足りない情報は推測で埋めず、質問にまとめて Deroshi に返す。
2. **大きさを判断する。**
   - **大きい Issue**：`AGENTS.md` の「人間確認が必要なとき」に当たる／3 ファイル以上にまたがる／仕様の不変条件・公開範囲・データ保護に触れる。→ 起票したら **実装に入らず** Deroshi の確認を待つ。本文の「補足」に「確認レベル：大」と書く
   - **小さいタスク（バッチ）**：既存パターンに沿う修正・文言・テスト追加など。→ 起票してそのまま `start-issue` に進んでよい
3. **1 Issue = 1 PR に収まる大きさに分ける。** 複数の独立した変更が混ざっていたら Issue を分ける。
4. **重複を確かめる。**
   ```sh
   <gh> issue list -R <リポジトリ> --state open --search "<キーワード>"
   ```
   同じ内容の Issue があれば起票せず、その番号を報告する。
5. **本文を一時ファイルに書いて起票する**（シェルの引用崩れを避けるため `--body-file` を使う）。
   ```sh
   BODY=$(mktemp)
   cat > "$BODY" <<'EOF'
   （下のテンプレを埋めた本文）
   EOF
   <gh> issue create -R <リポジトリ> --title "<タイトル>" --body-file "$BODY"
   rm -f "$BODY"
   ```
   ラベルは `<gh> label list -R <リポジトリ>` に既にあるものだけ `--label` で付けてよい。ラベル・マイルストーンの新規作成やアサインはしない。
6. **報告する**：Issue の番号・URL・タイトル、確認レベル（小／大）、次の一手（小なら `start-issue <番号>`、大なら「Deroshi の確認待ち」）。

## テンプレ

4 項目（背景 / スコープ / 受け入れ条件 / 対象外）は必須。書くことが無い項目も消さずに「なし」と書く。

```markdown
## 背景
<なぜ必要か。Deroshi の条件、発端になった事象・画面・ログ>

## スコープ
- <やること。変更するファイル・画面・リソースの見当>

## 受け入れ条件
- [ ] <第三者が確かめられる形で書く（例：「記録画面の2つのボタンが 48px 以上の高さで表示される」）>
- [ ] `<検証スキル>` の項目がすべて通る

## 対象外
- <今回やらないこと。混ざりやすい隣接タスク>

## 補足
- 確認レベル：小（起票→実装を通してよい）／大（実装前に Deroshi の確認が必要）
- 関連：#<番号>（あれば）
```

- **タイトル**：日本語で短く、何をするかが分かる形にする（例：「記録画面のボタンを大きくする」）。`start-issue` がこれを英訳してブランチ名のスラッグにする
- **受け入れ条件**：「いい感じにする」のような判定できない書き方をしない。数値・表示文言・コマンドの結果で書く

## してはいけないこと

- 4 項目のどれかを欠いたまま起票する
- `AGENTS.md` の不変条件・運用の前提を崩す内容を、そのまま起票する（先に Deroshi に相談する）
- Issue の本文にトークン・パスワード・秘密の値を書く
