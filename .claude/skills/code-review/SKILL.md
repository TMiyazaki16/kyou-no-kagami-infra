# code-review — PR を Issue・不変条件・テストと照合する

このスキルは汎用に書いてある。リポジトリ固有の値は、リポジトリ直下の `AGENTS.md` の「開発フロー」節にある **「スキルが参照する値」表** から読む（`<リポジトリ>`・`<gh>`・`<検証スキル>`・`<不変条件>`・`<変更禁止パス>`）。

## 原則

- **読むだけ。** レビュー結果はチャット（または Deroshi が指定したファイル）に出す。`gh pr review`・`gh pr comment`・`gh pr merge` は、Deroshi が「GitHub に投稿して」と明示したとき以外は実行しない
- **最終的なマージ判断は Deroshi が行う。** レビューには事実と根拠を書き、「マージしてよい／だめ」は書かない
- 指摘には必ず根拠（`path:line`、コマンドの出力）を付ける。推測は「推測」と明記する

## 手順

1. **PR を取得する。**
   ```sh
   <gh> pr view <PR番号> -R <リポジトリ> \
     --json number,title,body,state,headRefName,baseRefName,author,files,commits,closingIssuesReferences
   <gh> pr diff <PR番号> -R <リポジトリ> --name-only
   <gh> pr diff <PR番号> -R <リポジトリ>
   <gh> pr checks <PR番号> -R <リポジトリ>
   ```

2. **紐づく Issue を読む。** PR 本文の `Closes #<番号>`（または `closingIssuesReferences`）から：
   ```sh
   <gh> issue view <Issue番号> -R <リポジトリ> --json title,body,comments
   ```
   `Closes` が無い PR は、それ自体を指摘に挙げる。

3. **必要ならローカルで検証する**（作業ツリーがきれいなときだけ）。
   ```sh
   git status --porcelain            # 空であること
   <gh> pr checkout <PR番号> -R <リポジトリ>
   ```
   `<検証スキル>` を実行して結果を控える。終わったら元のブランチに戻る。PR ブランチに commit・push しない。

4. **照合する。**
   - **受け入れ条件**：Issue の各条件を「満たす／未達／確認できない」に分け、根拠を書く
   - **スコープ**：Issue の「対象外」に当たる変更、Issue と無関係な変更が混ざっていないか
   - **不変条件・運用ルール**：`<不変条件>` の各項目のうち差分に関係するものを 1 つずつ確かめる。関係しない項目は「該当なし」とする
   - **人間確認が必要な変更**：`AGENTS.md` の「人間確認が必要なとき」に当たる変更が、確認なしに入っていないか（Issue のコメントで確認済みかを見る）
   - **禁止事項**：`<変更禁止パス>` の変更、秘密の値・認証情報、`.gitignore` 対象ファイルの混入
   - **テスト**：新しい挙動にテストが足されているか、件数が期待値から想定どおり増減しているか、CI が通っているか
   - **形式**：ブランチ名が命名規則どおりか、PR 本文に `Closes #` とテスト・ビルド結果があるか
   - **正しさ**：バグ、境界条件、エラー処理、既存パターン（`AGENTS.md` の構成・書き方）からの逸脱

## 出力フォーマット

```markdown
# PR #<番号> レビュー：<タイトル>

- 対象 Issue：#<番号>（<タイトル>）
- ブランチ：`<head>` → `<base>`（命名規則：OK / NG）
- CI：<pass / fail / pending と各チェック名>
- ローカル検証：<実施した場合の結果。未実施ならその旨>

## 受け入れ条件
| # | 条件 | 結果 | 根拠 |
|---|---|---|---|
| 1 | … | 満たす / 未達 / 確認できない | `path:line` / コマンド結果 |

## 不変条件・運用ルール
| 項目 | 結果 | 根拠 |
|---|---|---|
| … | 守られている / 崩れている / 該当なし | … |

## テスト・ビルド
- <件数、追加されたテスト、CI の結果、足りないテスト>

## 指摘
### 要修正
- `path:line` — <問題> → <理由> → <修正案>
### 推奨
- …
### 軽微
- …

## Deroshi に確認してほしいこと
- <判断が要る点、仕様の解釈が分かれる点>

## まとめ
<事実の要約（受け入れ条件の充足数、要修正の件数、CI の状態）。マージ可否の判断は書かない>
```

指摘が無い区分は「なし」と書く。
